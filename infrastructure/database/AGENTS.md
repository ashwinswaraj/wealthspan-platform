# AGENTS.md — infrastructure/database

Migrations only, never touch directly. Falls back to root `AGENTS.md` for
anything not covered here.

## Current state

`config.toml` configures the **local Supabase CLI stack** (`project_id =
"wealthspan"`, local API on `54321`, local Postgres on `54322`, local Studio,
local auth pointed at `http://localhost:8080`). There is no `migrations/`
folder yet — the moment schema work starts, migrations belong here,
generated by the Supabase CLI (`supabase migration new <name>`), never
hand-written directly against a running database.

## Rules

- `[SEC]` **Never edit `config.toml`'s ports or `site_url` to point at a
  non-local environment.** This file is for local development only —
  staging/production Supabase config lives in the project's Supabase
  dashboard / environment secrets, not in this repo.
- `[RULE]` Every schema change ships as a migration file here, generated
  via the Supabase CLI — never as a manual `ALTER TABLE` run once against
  prod and left undocumented. This is what makes `packages/database`'s
  generated types (see its `AGENTS.md`) reproducible.
- `[SEC]` After any migration that changes a table's columns, regenerate
  `packages/database/src/types.ts` — a stale generated type is worse than
  no type, because it compiles but lies about the real schema.
- `[SCALE]` Seed data lives in `infrastructure/seed/seed-admin.ts`, not
  here — keep migrations (schema) and seeding (data) separate so
  migrations stay safely re-runnable in CI.

## Never do without confirmation

- Run a migration against anything other than the local Supabase stack
- Add a destructive migration (dropping a column/table) without confirming
  nothing still reads it — grep the whole repo, not just one app
- Change `[auth]` or `[api]` settings in `config.toml`
